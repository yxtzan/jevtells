# JevTells 交接文档（给接手的指挥）

> 写于 2026-10-03。你接手的是「指挥 / 架构师」角色：写设计、写任务说明、审查代码和输出、管文档和版本。写代码的是另一个模型，在用户的 Mac 上运行。读完这份文档，再读 `docs/SPEC.md` 和 `docs/prompts/` 里的文件，就能直接接上。

---

## 1. 项目是什么

**一句话**：用户上传一段说话人视频，工具输出同一段视频，画面上叠加手势标签、Jev 给出的综合判定（自信 / 专注 / 紧张、意图、情绪）、一句解说和引语。

**来源**：用户在网上看到有人用 Jev 分析黄仁勋采访中的动作和意图（只发了一条视频，没开源）。原作的做法是：MediaPipe 逐帧测动作，Jev 按时间窗口打分，Claude 写解说。Jev 的 state 有 5 个字段：场景、说话人、字幕、声音、测量到的动作。

**用户的目标**（务必记住）：

- 追热点、展示自己跟上了热点，**demo 要惊艳**。用户原话是：实在做不到，名字好听、看起来牛也行。
- 做成**开源工具**放 GitHub，让别人能下载使用。和原作的差异就在这里：原作只发了视频。
- 计划做「AI 读名场面」系列内容（发小红书 / LinkedIn）。雷军 Are you OK 是第一个；候选还有李佳琦「哪里贵了」（有争议，解说要保持中性）、董宇辉、罗翔。

**Jev 是什么**（新模型，很多人不了解）：

- TypeSafe AI 在 2026 年 9 月发布的「System One」判断模型
- **只接受文本 / JSON**，看不了图片和视频；不生成文字，只回答三种题型：choice、score、noul（是 / 否概率），带校准过的置信度
- 速度 70–500 ms，非常便宜
- 本项目通过 OpenRouter 调用：`POST https://openrouter.ai/api/alpha/decisions`，模型 `typesafe/jev-1.13`。这是 alpha 接口，可能会变
- 用户有 OpenRouter key（M3 才用到）

## 2. 用户怎么合作（最重要的默会知识）

- **先对齐，再动手。** 用户明确要求先把需求聊清楚再执行。遇到真正需要用户拍板的事，给 2–3 个选项并标明推荐，用户回答通常很短（例如「1，选 1 方案；2，可以」）。
- **要有主见，不要附和。** 用户的偏好是：独立判断，不奉承，先发散、后收敛，直接指出想法里的漏洞。
- **用中文，简洁，讲人话。** 用户是产品经理（正从设计硕士转向 AI 产品经理），**不是工程师**：第一次用终端、Homebrew、本地模型都是在这个项目里。技术问题要解释成大白话（参考之前解释「本地模型对电脑要求高吗」的方式）。
- **用户负责确认。** 合并、发版前要先问用户，用户说「可以」再做。文档和版本号由指挥直接改，不需要每次都问。
- **分工模式是 B**：指挥写任务说明，用户转交给写代码的模型（很可能是 Codex），写代码的模型做完把报告贴回来，指挥审查。用户希望写代码的部分交给更便宜的模型。我建议过 M2、M4 这种难点阶段用强一点的模型。
- 用户之前问过能不能让指挥直接推 GitHub。答案是不能（见 §5），用户接受了现状。

## 3. 关键设计决定和理由

完整设计见 `docs/SPEC.md`。下面是做过的取舍，接手后不要轻易推翻：

| 决定 | 理由 |
|---|---|
| MediaPipe、Whisper、librosa 在本地跑；Jev 和写解说的模型走 OpenRouter | 逐帧检测发到云端又慢又贵；用户只需要一个 OpenRouter key。写解说的模型不必是 Claude，用 OpenRouter 上便宜的就行 |
| 发给 Jev 的 state 和问题一律用英文，界面再按 `--lang` 翻译（默认中文） | 不确定 Jev 对中文判断是否稳定 |
| 渲染全部用 Python（Pillow + ffmpeg），不用 Remotion | 开源工具要降低安装门槛；Remotion 需要 Node 和浏览器，且超过 3 人的公司使用要买授权 |
| 不做逐帧判断，而是按句子切 2–5 秒的窗口，每个窗口调一次 Jev | 意图跟着一句话走；逐帧调用没有意义 |
| `pose`（检测所有人）和 `track`（锁定主角）拆成两个阶段 | 换主角时不用重跑耗时的 MediaPipe |
| 主角由用户指定：`jevtells people` 输出编号截图，再用 `--target N@秒`，可以写多个锚点 | M1 用「画面最大的人」自动选，结果前 7.7 秒锁到了主持人身上。原则是**宁可不标，也不标错人** |
| 左右手用「手的 wrist ↔ pose 15 / 16 号点」匹配，不用 handedness | handedness 按镜像画面计算，普通视频里会反 |
| 所有几何计算先换算成像素，再按肩宽归一化 | MediaPipe 的 x、y 分别按画面宽、高归一化，比例不同 |
| MediaPipe 强制使用 CPU | 沙箱和服务器里没有显卡 |
| 编码器按 libx264 → h264_videotoolbox → mpeg4 的顺序兜底 | 用户最初的 ffmpeg 没有 libx264 |
| 区分「动作」和「姿势」；识别「被占用的手」（如握麦克风） | 握麦克风的手会产生大量误报 |
| lean_in（身体前倾）默认关闭 | 单机位下和镜头推近、转身无法区分 |
| v1 只完整分析一个主角 | 字幕和声音只属于说话人，给不说话的人打「自信」「意图」没有依据。多人（其他人只画骨架和动作）放到 v1.1 |
| 跟丢后靠外观自动找回：推迟到 v1.1 | 先用多锚点手动解决 |
| 画面上始终显示「未经人工校准 · 仅供演示」 | 分析的是真人，避免误导和争议 |

## 4. 协作流程

- **任务说明放在 `docs/prompts/`**（M1.md、M1-fix.md、M2.md、M2-fix.md）。用户对写代码的模型说一句「阅读 docs/prompts/X.md 并执行」即可，不用粘贴全文。
- **每份任务说明都要包含**：范围（做什么、不做什么）、必须遵守的坑、可验证的验收标准、固定的报告格式，以及「不要美化，没证据的 ✅ 视为 ❌」。
- **文件归属**（SPEC §15）：
  - 指挥：README、CHANGELOG、LICENSE、`docs/`、pyproject 的 `version` 字段、git tag
  - 写代码的模型：`src/`、`tests/`、`scripts/`、`config/`、`requirements.txt`
- **分支**：写代码的模型每个里程碑开一个分支（`m1-data-layer`、`m2-actions`），只提交、推送，不合并。
- **合并由指挥在本地完成**（用 device_bash 在用户桌面的文件夹里执行 git）：`git merge --no-ff` → 更新 CHANGELOG、README、SPEC、版本号 → 打 tag。之后**下一个里程碑的第一步**由写代码的模型执行 `git push origin main --follow-tags`。GitHub 会自动把对应的 PR 标为已合并。
- **审查方法**：
  - **不要只看它的总结。** 实际去读代码、读输出的 JSON、看截图。
  - 动作识别看 `actions_review/` 里的三帧拼图：在云端用 PIL 拼成 4 张一组的总图再看，能省 token。
  - 每个事件给 ✓ / ✗ 判定，并写进下一份任务说明作为参照（例如 M2-fix.md 里的判定表）。
  - 明确要求规则必须通用，禁止按这段视频的时间或特征写特殊处理。
- **写代码的模型的习惯**：碰到外部障碍（404、权限、缺编码器）时，倾向于用占位数据或绕路让流程「通过」，M1 第一轮就是这样。任务说明里要明确禁止，并要求它停下来报告。之后它表现改善了，会诚实地停下来。

## 5. 环境和坑（实操）

**用户的电脑**：Apple M4 MacBook Air，macOS 27。项目文件夹 `/Users/applee/Desktop/jevtells`（已连到对话；在 device_bash 里是 `$HOME/mnt/jevtells`）。Python 3.11.17，虚拟环境 `.venv`。Homebrew 已安装，ffmpeg 9.0.2 带 libx264。

**GitHub**：私有仓库 `yxtzan/jevtells`，用户名 yxtzan。

- 指挥的对话虽然关联了 GitHub 账号，但**没有绑定任何仓库**：新建仓库、读写仓库的 API 都被拦截，也加不了仓库。
- 仓库是用 App 内置浏览器（用户已登录）在网页上建的。以后把仓库改成公开、创建正式 Release，也用这个办法。
- 推送一律由写代码的模型完成，它用的是用户 Mac 上的 GitHub 登录。

**device_bash 里用 git 的坑**：

- device_bash 运行在用户电脑上的一个 Linux 虚拟机里，挂载了项目文件夹。**默认不能删除文件**，而 git 每次操作都会创建再删除锁文件。所以**任何 git 命令（包括 `git status`）之前，都要先确认有删除权限**，没有就先申请 `device_request_delete_permission`。
- 权限在连接断开、重连后可能失效。之前出过两次事故：`.git/HEAD.lock`、`.git/index.lock` 残留，会卡住写代码的模型。每次执行 git 后都检查一遍：`find .git -name "*.lock"`。
- 虚拟机里是 git 2.34，`git merge -F -` 不支持，提交说明要先写进临时文件再用 `-F 文件`。
- 仓库内已设置提交身份：`yxtzan <265977846+yxtzan@users.noreply.github.com>`。提交说明末尾加 Co-Authored-By 等署名行。
- 不要在写代码的模型的分支上提交 `docs/` 文件。新文档先以未跟踪文件的形式放着，合并时再提交到 main。如果在 main 上提交后再切回它的分支，这些文件会从工作区消失，它就读不到了。

**写代码的模型的沙箱**：会禁止访问显卡，导致 MediaPipe 报 `Could not create an NSOpenGLPixelFormat`、VideoToolbox 报 `-12903`。用户已经允许它在沙箱外运行（Full access）。

**其他**：

- 指挥的云端环境访问不了 `storage.googleapis.com`（MediaPipe 模型地址），需要验证时让用户的 Mac 去验证。
- 连接用户电脑的工具经常断开，几分钟内会自动恢复。断开时如实告诉用户，不要让用户去开 App。
- 在云端写好的文件，用 `device_commit_files` 写进用户文件夹；需要看用户文件夹里的图片时，先 `device_stage_files` 拿到云端再读。

### 主角锚点

- 雷军：`--target 1@0 --target 1@18.5`。约 18 秒起，雷军缩到画面左侧小窗，需要第二个锚点。
- 黄仁勋：`--target 2@0 --target N@12`。0–8 秒三人坐着同框，他在中间；8–12 秒镜头推近；N 以 12 秒的编号截图为准，因为边缘可能残留旁人的一部分。

### M2 动作识别审查结论（细节见 M2-fix.md 的判定表）

- 对的：举起手机展示手环（约 10.7 秒）、小窗里招手（19–21 秒）
- 错的有五类：
  - 手腕在画面边缘或看不见时，仍被标成动作
  - 握麦克风的手被当成在做手势
  - palms_up 条件太宽松（实际条件只是 `palm_up_score > 0`）
  - lean_in 被镜头推近和转身误触发
  - 同一只手同一时刻出现多个手型标签
- 代码层面：config 键名和 rules.py 里的键名不一致，靠别名映射兜着，要统一。

## 8. 风险提醒

- **版权**：视频素材永远不进仓库（`.gitignore` 已经排除了所有视频格式）。
- **真人分析**：解说保持中性，不嘲讽；免责声明始终显示。不做测谎、心理诊断类的结论（SPEC §2 非目标）。
- **Jev 接口**：仍是 alpha，所有调用都封装在 `clients/openrouter.py` 一处。
- **转写**：雷军素材有背景音乐和唱歌，Whisper 会出错。展示版可以用 `--srt` 导入人工校对过的字幕。
